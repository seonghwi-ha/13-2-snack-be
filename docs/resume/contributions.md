## 2. 주요 작업 상세

### 2-1. 공통 에러 처리 구조 설계 (#5)

**문제**: 프로젝트 초기에 모듈마다 에러 응답 형태가 달라지면 프론트가 에러를 분기하기 어렵다.

**구현**

- `AppError(message, statusCode, code)`를 기반으로 `BadRequest / Unauthorized / Forbidden / NotFound / Conflict` 에러 클래스를 만들었다.
  서비스 레이어는 `throw new NotFoundError(...)`만 하면 된다.
- 전역 에러 핸들러에서 응답 형식을 `{ success: false, message, code }`로 통일했다.
  - 커스텀 에러는 `instanceof AppError`로 구분
  - Zod 검증 실패는 400이지만 `code: VALIDATION_ERROR`로 분리해, 비즈니스 규칙 위반과 스키마 오류를 응답만 보고 구분할 수 있게 함
  - 잘못된 JSON(`SyntaxError`) → 400
  - Prisma `P2002`(유니크 위반) → 409, `P2025`(대상 없음) → 404
  - 그 외 예외는 서버 로그에만 원인을 남기고 사용자에게는 일반 메시지만 노출
- 404 핸들러도 `NotFoundError`를 던지게 해서 모든 실패 응답이 한 경로를 지나게 했다.

**효과**: 이후 인증·주문·예산·초대·챗봇 등 10개 도메인 모듈이 모두 이 구조 위에서 에러를 던지고 있다.
`ConflictError`의 `code`로 `BUDGET_EXCEEDED`, `ORDER_ALREADY_PROCESSED` 같은 세부 상황을 표현한다.

### 2-2. 상품 API (#29, #43, #53, #56)

| Method | Path            | 설명                                        |
| ------ | --------------- | ------------------------------------------- |
| GET    | `/products`     | 목록 (검색·카테고리 필터·정렬·페이지네이션) |
| GET    | `/products/:id` | 상세                                        |
| POST   | `/products`     | 등록                                        |
| PATCH  | `/products/:id` | 수정 (본인 또는 관리자)                     |
| DELETE | `/products/:id` | 소프트 삭제 (본인 또는 관리자)              |
| GET    | `/me/products`  | 내가 등록한 상품                            |

**설계 포인트**

- **멀티 테넌시(조직 격리)**: 모든 조회·수정 쿼리에 `organizationId`를 넣었다.
  등록할 때 조직 id는 body로 받지 않고 토큰에서 꺼낸다. body로 받으면 다른 회사에 상품을 등록할 수 있기 때문이다.
- **권한 검사**: 수정·삭제 전에 `assertCanModify`로 "등록자 본인 또는 ADMIN 이상"인지 확인한다.
  대상이 없으면 404, 권한이 없으면 403으로 구분했다.
- **무한 스크롤 대응 정렬**: 최신순·인기순·가격순 정렬 모두 마지막 정렬 키로 `id`를 붙였다.
  정렬 값이 같은 상품이 페이지 경계에 걸리면 순서가 흔들려 같은 상품이 중복되거나 누락되기 때문이다.
  응답에는 `hasNext`를 넣어 프론트가 다음 페이지 요청 여부를 바로 판단하게 했다.
- **카테고리 2단 필터**: `categoryId`는 소분류 하나만, `parentCategoryId`는 대분류 아래 전체를 조회한다(관계 필터 `category.parentId`).
- **목록 조회 성능**: `findMany`와 `count`를 `Promise.all`로 병렬 실행했다.
- **타입 안전한 select**: `satisfies Prisma.ProductDefaultArgs`와 `Prisma.ProductGetPayload`로 select 정의에서 응답 타입을 바로 뽑아,
  필드를 추가하면 타입이 함께 바뀌게 했다.
- **찜 개수**: Prisma `_count`로 찜 수를 한 쿼리에서 집계하고, 응답은 `_count.wishlistItems` 대신 `wishlistCount`로 펴서 내보냈다.
- **`isMine`**: 프론트가 수정·삭제 메뉴를 본인에게만 보여줘야 하는데 `GET /me`가 id를 주지 않아서, 상세 응답에 본인 여부를 계산해 넣었다.

**입력 검증 (Zod)**

- `z.coerce.number()`는 `null`·빈 문자열을 `0`으로 바꿔버려서, **가격을 비워 보내면 0원 상품이 저장되는 버그**가 있었다.
  전처리 함수로 숫자나 비어 있지 않은 문자열만 통과시켜 "값 없음"과 "0"을 구분했다.
- 수정 모달에서 이미지·링크를 지울 수 있도록 `''`과 `null`을 받고, 저장할 때는 `null`로 통일했다.
- 이미지 주소는 외부 URL과 내부 이미지 API 경로(`/api/images/...`)를 둘 다 허용했다 (#41).
- 존재하지 않는 카테고리 id는 Prisma가 FK 위반(`P2003`)을 던져 500이 되므로, 서비스에서 미리 확인해 400으로 응답했다.
- 마지막 페이지를 넘는 요청은 400. 단, 결과가 0건이어도 1페이지는 빈 목록으로 응답한다.

### 2-3. S3 이미지 업로드·조회·삭제 (#34)

| Method | Path           | 권한            |
| ------ | -------------- | --------------- |
| POST   | `/images`      | 로그인          |
| GET    | `/images/*key` | 공개 (UUID key) |
| DELETE | `/images/*key` | ADMIN 이상      |

**설계 포인트**

- **프라이빗 버킷 + API 프록시**: 버킷은 공개하지 않고, 조회는 서버가 `GetObject` 스트림을 그대로 응답으로 흘려보낸다.
  나중에 CloudFront나 presigned URL로 바꿀 때 `getImageUrl()` 한 곳만 고치면 되도록 주소 생성을 분리했다.
- **업로드 검증**: `multer-s3`로 바로 S3에 올리며 필드명·1장·5MB·jpg/png/webp/gif로 제한했다.
  파일명은 한글·공백·중복 문제를 피하려고 UUID로 새로 만들고 확장자는 MIME 타입에서 정한다.
  `MulterError`는 전역 핸들러가 모르는 에러라 500이 되므로, 미들웨어에서 사유별 400 메시지로 바꿨다.
- **S3 클라이언트 지연 생성**: 모듈 로드 시점에 만들면 `AWS_REGION`이 없을 때 서버가 아예 뜨지 않는다.
  AWS 설정이 없는 팀원도 서버를 켤 수 있게 첫 요청 때 만들고, 빠진 환경변수 이름을 에러 메시지로 알려준다.
  EC2에서는 액세스 키 없이 IAM 역할을 쓰도록 SDK 기본 자격 증명 체인에 맡겼다.

**트러블슈팅**

1. **목록 이미지가 일정 시간 후 깨지는 문제**
   - 원인: 액세스 토큰이 15분이라 목록을 오래 띄워두면 지연 로딩되는 이미지 요청이 401이 된다.
     `<img>`·`next/image` 요청은 프론트 fetch 클라이언트를 거치지 않아 토큰 재발급도 안 된다.
   - 해결: 조회 API에서 인증을 뺐다. key가 UUID라 주소를 모르면 열 수 없고, 버킷은 계속 프라이빗으로 유지된다.
2. **없는 이미지 요청에 403이 오는 문제**
   - 원인: IAM에 `s3:ListBucket` 권한이 없으면 S3는 없는 key에 404 대신 403 AccessDenied를 준다.
   - 해결: `NoSuchKey`와 403을 모두 404로 맞추되, 403은 버킷명·리전·권한 설정 오류일 수도 있어 서버 로그는 남겼다.

### 2-4. 시드 데이터 정비 (#45, #47, #49)

- 프론트가 카테고리를 상수로 들고 있어 시드를 돌릴 때마다 id가 바뀌면 필터가 어긋났다.
  → 기획서 기준 대분류/소분류를 **id 고정**으로 넣고, 이후 생성분과 충돌하지 않게 시퀀스를 200부터 다시 시작하도록 했다.
  대분류를 먼저 넣어 소분류의 `parentId` FK가 걸리지 않게 순서를 맞췄다.
- 상품 카탈로그를 `seedCatalog.ts`로 분리하고 공식 상품 이미지를 연결했다.
- 일반 회원이 등록한 상품, 여러 품목이 담긴 장바구니·주문 데이터를 추가해 권한·주문 화면을 실제처럼 검증할 수 있게 했다.

## 4. 자소서용 요약 문장 (초안)

- 공통 에러 클래스와 전역 에러 핸들러를 설계해 팀 전체 10개 도메인 모듈의 실패 응답 형식을 하나로 통일했습니다.
- 상품 API에서 정렬 키에 고유 id를 덧붙여 무한 스크롤 시 상품이 중복·누락되는 문제를 막았습니다.
- `z.coerce`가 빈 값을 0으로 바꿔 0원 상품이 저장되던 버그를 찾아, "값 없음"과 "0"을 구분하는 전처리로 해결했습니다.
- S3 버킷을 프라이빗으로 유지하면서 토큰 만료로 이미지가 깨지는 문제를 UUID key 기반 공개 조회로 풀었습니다.
- 업로드 기록 테이블과 정리 스케줄러를 도입해, 상품에 쓰이지 않고 S3에 쌓이던 이미지를 매일 자동으로 정리했습니다.
- 오프셋 페이지네이션을 커서 방식으로 확장해, 스크롤 중 상품이 추가돼도 이미 본 상품이 다시 나오지 않게 했습니다.
- pg_trgm 유사도로 오타 검색에 "혹시 이 상품을 찾으셨나요?" 추천을 붙이고, 짧은 한글 상품명에 맞게 기준값을 실측해 조정했습니다.
- Redis 캐시로 상품 목록 첫 화면 응답을 342ms에서 1.5ms로 줄이고, Redis 장애 시에도 DB로 바로 응답하도록 설계했습니다.
- 상품 변경과 같은 트랜잭션에서 바뀐 필드만 이전·이후 값으로 남기는 감사 로그를 만들어, 누가 언제 무엇을 바꿨는지 추적할 수 있게 했습니다.
- 저장된 이미지 주소를 바꾸지 않고 조회 API의 302 리다이렉트로 presigned URL·CloudFront 제공 방식을 추가해, 데이터 이전 없이 이미지 트래픽을 서버에서 분리할 수 있게 했습니다.
- 테스트를 5개에서 118개로 늘리는 과정에서 잘못된 이미지 주소에 안내 문구 대신 `Invalid input`이 나가던 검증 버그를 찾아 고쳤습니다.

## 5. 포크 이후 추가 작업 (개인)

팀 프로젝트가 끝난 뒤 포크 저장소에서 남은 과제를 이어서 진행했다.

### 5-1. 단위 테스트 체계 구축

- 팀 저장소의 테스트는 `authToken.test.ts` 하나(5개)였다. 상품 서비스·스키마, 이미지 서비스, 전역 에러 핸들러 테스트를 추가해 **64개**로 늘렸다. (이후 고급 기능 작업까지 포함해 118개)
- repository와 S3 클라이언트를 `jest.mock`으로 대체해 DB·AWS 없이 서비스 규칙만 검증한다.
  (페이지네이션 경계, `isMine`, 조직 격리, 수정·삭제 권한, 빈 가격 거부 등)
- **테스트로 찾은 버그**: 이미지 주소가 잘못되면 "올바른 이미지 주소가 아닙니다." 대신 Zod 기본 메시지 `Invalid input`이 나갔다.
  내부 경로(regex)와 외부 URL 두 문자열 후보가 모두 실패하면 Zod 4가 union 오류로 묶어버리기 때문이었다.
  union 자체에 메시지를 지정해 해결했다.

### 5-2. 이미지 소유권 기록과 고아 이미지 정리

**문제**: 업로드한 이미지가 DB에 기록되지 않아 누가 올렸는지 알 수 없었다.
그래서 삭제는 관리자만 가능했고, 상품 등록을 취소하거나 이미지를 바꾸면 이전 파일이 S3에 영원히 남았다.

**구현**

- `Image` 테이블(key, 업로드한 사람, 조직) 추가 및 마이그레이션
- 업로드 시 기록. 기록이 실패하면 아무도 지울 수 없는 파일이 되므로 S3 파일을 바로 삭제한다.
- 삭제 권한: 업로드한 본인 또는 같은 조직 관리자. 다른 조직 이미지는 존재 여부를 숨기려고 404.
  테이블 도입 전 이미지는 업로더를 알 수 없어 기존처럼 관리자만 허용(하위 호환).
- 삭제 순서를 **S3 → DB**로 정했다. S3가 실패하면 DB는 그대로라 재시도할 수 있고,
  DB가 실패해도 기록이 남아 정리 작업이 다시 지운다(DeleteObject는 멱등).
  삭제한 이미지를 쓰던 상품의 `imageUrl`은 같은 트랜잭션에서 비운다.
- `node-cron`으로 매일 04시(KST), 업로드 후 24시간이 지났는데 어떤 상품도 쓰지 않는 이미지를 S3·DB에서 정리한다.
  - 소프트 삭제된 상품도 구매 내역 화면에서 이미지를 보여주므로 사용 중으로 본다.
  - id 커서로 100개씩 나눠 처리하고, 한 파일이 실패해도 나머지는 계속 지운 뒤 실패한 기록은 다음 실행에 다시 시도한다.
  - AWS 설정이 없는 로컬 환경에서는 스케줄러를 등록하지 않는다.
- 로컬 PostgreSQL에 마이그레이션을 적용하고 시드 데이터로 저장소 쿼리(사용 중 판별, 상품 imageUrl 정리)를 직접 확인했다.

### 5-3. 외래키 위반 응답 정리

- 없는 대상 id를 가리키는 요청에서 Prisma `P2003`이 500으로 나가던 것을 전역 핸들러에서 400 `INVALID_REFERENCE`로 바꿨다.
  Prisma 7 + `adapter-pg` 환경에서 실제로 `P2003`이 발생하는지 로컬 DB로 확인했다.

### 5-4. 커서 기반 페이지네이션

**문제**: 무한 스크롤이 오프셋(`skip`) 방식이라 뒤 페이지로 갈수록 앞의 행을 모두 읽고 버리고,
스크롤 중에 새 상품이 등록되면 다음 페이지 첫 상품이 이미 본 상품으로 다시 나왔다.

**구현**

- 마지막으로 본 상품의 "정렬 값 + id"를 base64url 커서로 내려주고, 다음 요청은 그 뒤부터 읽는다.
  모든 정렬이 마지막 키로 id 내림차순을 쓰기 때문에 정렬 값이 같아도 다음 행이 하나로 정해진다.
  (예: 낮은 가격순은 `price > v OR (price = v AND id < 마지막 id)`)
- `limit + 1`개를 읽어 다음 페이지 여부를 판단해, 커서 방식에서는 페이지 계산이 필요 없다.
- 기존 프론트를 깨지 않도록 `page` 방식은 그대로 두고 응답에 `nextCursor`만 추가했다.
  첫 화면은 page로, 이후는 커서로 이어갈 수 있다.
- 커서에 정렬 이름을 담아, 정렬을 바꾼 뒤 옛 커서를 보내거나 조작한 값은 400 `INVALID_CURSOR`로 거부한다.
- 정렬별 `(organizationId, 정렬 컬럼, id)` 복합 인덱스를 추가했다.

**검증**: 로컬 DB에서 동점이 많은 데이터로 4가지 정렬을 7개씩 끝까지 넘겨, 전체 정렬 결과와 순서가 같고 중복이 없음을 확인했다.
스크롤 도중 상품을 추가하는 시나리오에서 오프셋은 이미 본 상품이 다시 나왔고 커서는 나오지 않았다.

### 5-5. 상품명 검색 고도화 (pg_trgm)

- `pg_trgm` 확장과 상품명 GIN 트라이그램 인덱스를 추가했다. 기존 `ILIKE '%키워드%'` 검색이 쿼리 변경 없이
  인덱스를 탄다(실행 계획으로 확인). 단, 2글자 키워드는 트라이그램이 만들어지지 않아 인덱스로 좁힐 수 없다.
- 검색 결과가 0건이면 `word_similarity`로 비슷한 상품명을 최대 5개 `suggestions`로 준다.
  결과가 있을 때는 추가 쿼리를 하지 않는다.
- **기준값 튜닝**: 기본값 0.6은 짧은 한글 이름의 한 글자 오타('새우강'↔'새우깡' = 0.5)도 놓쳤다.
  실제 시드 데이터로 유사도를 재 보고, 절대 기준 0.25와 "최고 점수의 80% 이상" 상대 기준을 함께 써서
  '코가콜라'→코카콜라는 잡으면서 '포카침'→'3M 포스트잇' 같은 엉뚱한 추천은 걸렀다.

### 5-6. Redis 상품 목록 캐시

- 홈과 카테고리 탭에서 가장 많이 부르는 "조직 전체 첫 화면 목록"만 60초 캐시한다.
  검색어(조합이 많아 적중률 낮음)와 내 상품 목록(사용자별)은 담지 않는다.
- **무효화**: 패턴으로 키를 찾아 지우는(SCAN) 대신 조직별 버전 키를 캐시 키에 넣고, 데이터가 바뀌면 버전만 올린다.
  상품 등록·수정·삭제뿐 아니라 응답에 들어 있는 찜 수·구매 수가 바뀌는 찜 추가·삭제와 구매 승인에서도 올린다.
  DB 커밋 뒤에 버전을 올려, 다른 요청이 새 버전 키에 옛 데이터를 담는 경쟁 상태를 막았다.
- **장애 대응**: 캐시는 없어도 되는 기능이라 Redis 문제로 요청이 느려지면 안 된다.
  오프라인 큐를 끄고 명령 제한 시간을 300ms로 두어, 실패는 캐시 미스로 보고 DB에서 읽는다.
  `REDIS_URL`이 없으면 캐시를 아예 쓰지 않아 기존 환경도 그대로 동작한다.
- JSON에는 Date가 없어서 캐시에서 꺼낸 `createdAt`이 문자열이 되는 문제를, `...At` 필드의 ISO 문자열만 Date로 되살려 해결했다.
- **검증**: 실제 Redis로 첫 요청 342ms → 캐시 적중 1.5ms, 찜·등록 직후 즉시 반영, Redis 중단 후에도 3.7ms에 DB로 응답함을 확인했다.

### 5-7. 상품 변경 이력 (감사 로그)

- `ProductHistory` 테이블에 작업 종류(등록·수정·삭제), 작업자, 시각, 변경 내용을 남긴다.
- **원자성**: 상품 변경과 이력 기록을 같은 트랜잭션에서 처리해, 변경은 됐는데 이력이 없는 상태가 생기지 않는다.
- **변경 내용 최소화**: 수정 요청 전 값을 트랜잭션 안에서 읽어, 실제로 바뀐 필드만 `{ before, after }`로 남긴다.
  같은 값을 다시 저장한 요청은 기록하지 않고, 값을 비운 것(`null`)과 보내지 않은 것(`undefined`)을 구분한다.
  구매 수처럼 시스템이 바꾸는 값은 기록 대상에서 뺐다.
- `GET /products/:id/history`: 감사용이라 같은 조직의 관리자 이상만 보고, 삭제된 상품의 이력도 조회된다. id 커서로 페이지를 넘긴다.
- **검증**: 서버를 띄워 등록 → 수정 → 같은 값 재저장 → 삭제 후 이력이 3건(같은 값 재저장 제외)만 남고, 수정 이력에 바뀐 필드만 있음을 확인했다.

### 5-8. 이미지 제공 방식 확장 (presigned URL · CloudFront)

**문제**: 이미지 조회가 모두 서버를 거쳐 S3 스트림을 중계해서, 이미지 트래픽이 EC2 대역폭과 메모리를 쓴다.
그런데 상품 `imageUrl`이 이미 DB에 `/api/images/<key>`로 저장돼 있어서, 주소를 바꾸려면 데이터 이전이 필요했다.

**구현**

- 저장된 주소는 그대로 두고, 조회 API가 설정에 따라 이미지를 직접 주는 대신 **302 리다이렉트**하게 했다.
  `<img>`와 `next/image`는 리다이렉트를 따라가므로 프론트와 데이터 모두 바꿀 필요가 없다.
- `IMAGE_CDN_BASE_URL`이 있으면 CloudFront 주소로, 없으면 1시간 유효한 S3 presigned URL로 보낸다. 기본값은 기존 중계 방식이다.
- presigned URL은 요청마다 달라 공용 캐시에 담기면 안 되므로 `private`, 만료 5분 전까지만 재사용하도록 캐시 헤더를 정했다.
- 설치만 돼 있고 쓰이지 않던 `@aws-sdk/s3-request-presigner`를 활용했다.
- **검증**: 가짜 자격 증명으로 실제 서명 URL(만료·서명 형식)을 단위 테스트하고, 서버 HTTP 응답의 302·Location·Cache-Control을 확인했다.
  실제 AWS 버킷과 CloudFront 연결은 이 환경에서 확인하지 못했다.
